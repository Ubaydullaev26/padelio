# 15 · Выбор технологического стека

Решения приняты по критериям из [док. 08 §6](08-architecture.md): скорость маленькой команды, зрелые библиотеки Telegram/платёжек, надёжные транзакции, один язык, найм в УЗ, «скучные» технологии.

## Итоговый стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Язык | **TypeScript везде** (клиент + сервер + бот) | Один язык на всё → общие типы API-контрактов, взаимозаменяемость 2 fullstack-разработчиков, большой рынок найма в УЗ |
| Backend | **Node.js + NestJS** | Модульный монолит из коробки (модули = границы из ADR-1), DI, понятная структура для роста команды; зрелая экосистема |
| БД | **PostgreSQL 16** | Ключевой аргумент: **EXCLUDE-констрейнты (btree_gist) на пересечение интервалов** — анти-double-booking на уровне БД (ADR-3) реализуется штатно; транзакции, JSONB, полнотекстовый поиск |
| Доступ к БД | **Drizzle ORM + SQL-миграции** | Лёгкий, типобезопасный; EXCLUDE-констрейнты и партицирование пишем сырым SQL в миграциях — Drizzle этому не мешает (в отличие от Prisma) |
| Кэш / очереди | **Redis + BullMQ** | Hold-таймеры (TTL), очереди уведомлений/джобов (истечение hold, напоминания, reconciliation), rate limiting |
| Реальное время | **SSE (Server-Sent Events)** | Односторонний поток «обновления расписания» — SSE проще WebSocket, работает через прокси, автопереподключение; fallback — поллинг 15 с |
| Mini App | **React + Vite + TypeScript** | Стандарт индустрии, найм; Vite — скорость сборки |
| UI/состояние | **Tailwind CSS + TanStack Query** | Быстрая вёрстка под тему Telegram (CSS-переменные `--tg-theme-*`); Query — кэш серверного состояния, ретраи, инвалидация |
| Telegram SDK | **@telegram-apps/sdk-react** (Mini App) + **grammY** (бот) | Самые зрелые TS-библиотеки; grammY — очереди, middleware, типы Bot API |
| Панель платформы | React + **Refine** (или AdminJS) | Готовый каркас CRUD-админки — не тратим спринты на внутренний инструмент |
| Карты | **Yandex Maps JS API** (осн.) | Лучшее покрытие Ташкента и геокодинг; deep-links маршрутов: Яндекс/Google/2GIS на выбор пользователя |
| Хранилище файлов | S3-совместимое (**Cloudflare R2**) + Cloudflare CDN | Дёшево, без платы за трафик; pre-signed загрузки; ресайз — воркер (sharp) |
| Платежи | Прямые интеграции **Payme Merchant API + Click Merchant API** (MVP), Uzum/Telegram Payments — v2 | Прямые интеграции надёжнее посредников; адаптеры за единым интерфейсом `PaymentProvider` (ADR-5) |
| Монорепо | **pnpm workspaces + Turborepo** | `apps/api, bot, miniapp, admin` + `packages/shared` (типы, контракты, i18n-словарь) |
| CI/CD | GitHub Actions → Docker-образы → деплой по SSH (docker compose) | Просто, дёшево, воспроизводимо |
| Хостинг | **1 VPS (Hetzner, Германия) на старте**: API+бот+воркеры, managed/локальный Postgres с ежедневными бэкапами в R2; статика Mini App — Cloudflare Pages | Латентность UZ→Франкфурт ~90 мс — приемлемо для API; ⚠️ решение пересматривается, если юрпроверка потребует локализации ПДн в УЗ (тогда локальный ЦОД для БД) |
| Наблюдаемость | **Sentry** (ошибки) + **Grafana/Prometheus или Uptime Kuma** + бизнес-алерты в Telegram-канал команды | Алерт «0 броней в прайм» важнее CPU (док. 08 §5) |
| Аналитика продукта | Событийная таблица в Postgres + **Metabase** (MVP); PostHog — позже | Не плодить инфраструктуру до появления объёмов |
| Тесты | Vitest (юнит), Testcontainers (конкурентные тесты броней на реальном Postgres — обязательны в CI), Playwright (e2e критичного пути) | Ядро броней/денег — только с тестами конкурентности (док. 11) |

## Рассмотренные альтернативы (и почему нет)

- **Python (FastAPI + aiogram):** отличный вариант, много Python-разработчиков в УЗ; минус — два языка (фронт всё равно TS), нет общих типов. Допустимый план Б, если найм под TS-бэкенд забуксует.
- **Go:** производительность не нужна на этой нагрузке, скорость разработки продукта ниже.
- **Prisma вместо Drizzle:** тяжелее с нестандартным SQL (EXCLUDE, партиции), генератор миграций конфликтует с ручными.
- **WebSocket (Socket.IO):** двусторонность не нужна для расписаний; SSE дешевле в эксплуатации.
- **Kubernetes / микросервисы / managed-облака AWS-класса:** налог на маленькую команду; docker compose на VPS покрывает первые ×100 роста (ADR-1).
- **Firebase/Supabase как ядро:** бизнес-логика броней и денег требует полного контроля транзакций; вендор-лок на старте опасен.

## Скелет монорепо

```
padelio/
├── apps/
│   ├── api/        # NestJS: модули booking, catalog, payments, identity,
│   │               # notifications, reviews, club-ops, analytics
│   ├── bot/        # grammY: /start, deep-links, доставка уведомлений (консюмер BullMQ)
│   ├── miniapp/    # React+Vite: игрок + режим клуба (ролевой роутинг)
│   └── admin/      # React+Refine: панель платформы (2FA)
├── packages/
│   ├── shared/     # типы домена, контракты API (zod-схемы), константы, i18n-словари
│   └── ui/         # общие компоненты miniapp/admin
├── infra/          # docker-compose, миграции SQL, скрипты бэкапов, grafana
└── docs/           # эта документация
```

## Первые технические задачи (Sprint 1, из этого документа)

1. Инициализация монорепо, CI (lint, typecheck, тесты), окружения dev/stage/prod.
2. Docker-compose: Postgres + Redis + api + bot; сиды тестовых данных.
3. Миграция ядра БД с EXCLUDE-констрейнтом + конкурентный тест (100 параллельных броней одного слота → ровно 1 успешна).
4. Авторизация: проверка initData (HMAC, TTL) → сессионный JWT; каркас RBAC.
5. Каркас Mini App: роутинг, тема Telegram, i18n (uz/ru), TanStack Query, заглушки экранов.
